# 主界面与章节导航

识别主界面所有 UI 按钮，从主界面点击【调查】进入主线，在章节选择页拖动选章，进入章节关卡列表。模板直接从实机截图裁出（`samples/`），流程文件由脚本生成。

## 在助手里使用

两个新任务（`interface.json`）：

| 任务 | 选项 | 作用 |
| --- | --- | --- |
| 主界面按钮识别测试 | 主界面按钮（23 个） | 在主界面识别所选按钮并点击一次，用来核对每个按钮的识别和点击位置 |
| 进入主线章节 | 目标章节、关卡难度页签、到达关卡列表后 | 主界面 → 调查 → 选章 → 关卡列表；可从主界面、章节选择页或关卡列表开始 |

「到达关卡列表后」选【点击最新关卡并自动推剧情】会交给原有的 `StoryEntryRouter` 流程。

## 识别的内容

- 主界面：调查、唤醒体、编队、物资、幕间演习、学期课题、守密纪行、学籍档案、秘典书库、记忆回廊、幻梦深潜、相位对弈、融灾禁区、密境课堂、弥萨格商店、设置、主页图标、邮件、好友、左侧两个功能图标；两个活动横幅（内容每天变，只按固定位置点击，不做图像识别）。
- 小图标按钮（设置、主页、邮件、好友、左侧图标）要求同时识别到唤醒体/编队/物资，避免在其他页面误触发。
- 章节选择页：「调查行动」标题；关卡列表页：底部「共鸣/星级评分/关卡成就」栏；右上罗盘（返回）。

## 章节选择怎么走

没有 OCR，所以按「先回第 1 章、再数着往后拖」：向右连续拖 9 次（到头后不再变），再向左拖 N-1 次。目标章节中央的数字有模板时会校验，不一致就报错停止，不会进错章节。

**目前只有第 8 章有数字模板**（实机截图里只有它居中）。其余章节不校验，拖动次数不对就会进错章。补模板：在章节选择页让第 N 章居中，截图后运行

```
python tools/make_chapter_template.py 截图.png N
python tools/build_nav_pipeline.py
```

模板只裁数字的最后一位（前面的 0 每章相同）。模板作为第 9 章的数字时从侧卡裁的版本在居中时得分不够区分，所以没有保留。

## 活动扫荡（重现）

任务「活动扫荡（重现）」：在活动关卡列表（如巨古誓言）滚到底部 → 选中最后一项（癫狂）上面的那一关 → 点金色【重现】→ 在【重现次数】窗口点最大次数（↑）→ 点【确定】→ 点空白处关闭【重现奖励】。可从关卡列表、重现窗口、奖励弹窗开始，也可从活动关卡页开始（先点节点 1–5，设置「扫荡节点」）。

`sweep_ui.json` 描述识别内容，`python tools/build_sweep_pipeline.py` 生成 `resource/pipeline/sweep.json` 和 `resource/image/sweep_*.png`；`python tools/test_sweep.py` 在 3 张实机截图（关卡列表、重现窗口、重现奖励）加活动关卡页等页面上跑 91 项，涵盖各节点只在对应页命中、点击位置、从列表/重现窗口/奖励弹窗/活动关卡页开始的 4 条完整流程，以及没有【重现】时先挑战的流程。

没有验证的：
- **最大次数**：点击 ↑ 后次数是否变成最大值（样本里是 1/24）没有识别，因为没有「最大后」的样本；若体力不足，最大值可能小于 24，流程照样点确定。
- 体力不足、重现次数为 0 或「确定」置灰时的画面没有样本，会在点确定后等不到奖励弹窗而超时。
- 选中「癫狂上面的关卡」靠滚到底后固定位置点击，不识别关卡名称；列表项数量变化（新增难度）会选错。
- 重现奖励弹窗点空白处关闭，没有测试弹窗需要点两次的情况（测试里只点了一次）。
- 样本里的关卡「之六」已通关；未通关的关卡可能没有【重现】按钮（金色按钮可能是别的文字），此时流程在等待【重现】处超时。

### 没有【重现】时先挑战通关一次

选中「癫狂上面的关卡」后，如果没有金色【重现】（关卡从未通关），流程点蓝色【挑战】（不用助战），交给原有的编队/调查/战斗/结算节点，通关结算后回到关卡列表，再找一次【重现】；仍然没有就停止（`Sweep_Fail`）。挑战失败（走到「止步于此」）也停止（`Sweep_GiveUp`）。这两处依赖任务级覆盖（`interface.json` 里「活动扫荡」任务的 `pipeline_override`）：把原循环里「完成调查/止步于此」之后的去向改回扫荡，否则会接着开始同调率刷取。另外【重现次数】窗口点【确定】只重试一次，窗口还在就超时停止，不会无限循环。

没有验证的：未通关关卡的真实画面没有样本（【重现】位置是否显示别的按钮、【挑战】是否在同一位置）；用修掉了金色按钮的已通关截图模拟。通关后结算页的点击沿用原流程。

## 自动推进主线

任务 `自动推进主线`（`resource/pipeline/mainline.json`，由 `tools/build_mainline_pipeline.py` 按 `mainline_ui.json` 生成）：

1. 章节关卡列表：先看左下角【共鸣】红点 → 点开共鸣页 → 点红点节点 → 点【激活】→ 回到共鸣页，循环到没有红点 → 点右上角 X 退出；然后点最右侧最新关卡。
2. 进关后沿用剧情/战斗/走格子逻辑（`StoryInsideRouter` 等），地图上看不到下一步时在绿色描边的可选格里选一格（选格方式可设：随机/最上/最下/最左/最右）。
3. 通关回到关卡列表后重复第 1 步，继续推进。
4. 停止条件：战斗超过「主线战斗超时」（默认 4 分钟，视为不能自动的 boss）→ 弹窗"需要手动操作"；出现失败/灵知不足页 → 弹窗"练度差距过大，请重新配队或沉淀"；走格子长时间无进展 → 弹窗"卡住了"。弹窗为 Windows `MessageBox`（PowerShell）。

测试：`python tools/test_mainline.py`（真实截图 + MaaFramework，不需要游戏）。

没有实机验证的部分：
- 选格是随机点绿色描边格，没有"点后是否有变化"和锁门检测，靠卡住保护兜底。
- boss 只靠战斗超时识别；"没灵知"靠失败页出现推断。
- 共鸣石不足时点【激活】会怎样没有样本；通关结算页回关卡列表的流程也没有样本。
- 弹窗命令只在测试里验证了编码内容，没在 Windows 上实跑。
- 付费复活弹窗（应急灵知体耗尽后的材料兑换）：主线任务把 `AA_PaidRevive`（来自活动推进的实机验证）排在 `StoryReviveDecision` 前面，出现时弹窗预警并停止，不会点击兑换确认。该组合只在合并后的资源里做了结构校验和流程测试，没有在主线里实机触发过。

## 活动推进（可配置，适配其他活动）

「自动活动推进」由 `resource/navigation/activity_profiles/*.json`（每个活动一份）经 `tools/build_activity_advance.py` 生成，当前自带 `aa.json`（倘若荣光不复，9 关；重构前后生成的流水线逐字一致，只多了下面的通用兜底）。

合并与通用化：
- 入口：原来只认「倘若荣光不复」专属的列表项/金色入口图；现在认不到就落到同调率循环用的通用节点（`ActSlot` 选活动列表第几项、`ActEntry` 点左/右玩法入口），任务里带了「活动列表项」「活动玩法入口」两个选项。通用入口落到的关卡页也会被识别为本活动的关卡页。
- 关卡序列由配置决定：关卡数、每关点击位置、点击前的滚动（`reset_swipes` + 每关 `swipes`）。
- 任务列表里只有一个「活动自动推进」任务，推进哪些关卡放在它的选项「活动推进范围」里（全部 / 第 1–N 关中的某一关），不再每关一个任务。
- 不再要求每关都有标题模板：没有 `title` 的关卡按顺序结算（`AA_CompletedN` 只能命中一次），有 `title` 的仍按标题+癫狂选中判断。
- 付费复活预警、战败即停、应急灵知体选项、之六→癫狂的难度策略对所有活动共用。
- 多个活动互不冲突：每份配置有自己的节点前缀和流水线文件。

适配新活动：复制 `_template.json` 为 `<id>.json`，改 `id`/`prefix`/`task_all`/`scope_option`/`stages`/模板图名，把需要的模板截图放进 `resource/image/`，运行 `python tools/build_activity_advance.py`，再跑 `python tools/test_activity_advance.py` 做结构检查，最后用 `tools/verify_activity_advance.py` 实机验证。

没有验证的部分：新增的通用入口兜底、按顺序结算（`max_hit`）都只做了结构测试，没有实机跑过；换活动时关卡页模板、关卡坐标和滚动方式必须按新活动的截图重新填。

## AUTO 点击逻辑（story_demo / sync_rate 共用）

问题：旧流程只用灰色版 `auto_off_text.png`（阈值 0.75）判断，一张完整战斗截图里亮起的 AUTO 也能命中（0.758），而且只等 0.65 秒就判断"没亮"并补点，容易把已经开启的 AUTO 点回关闭，形成反复点击。

现在：
- 「已亮起」= 亮起版文字模板 `auto_on_text.png` 在位且文字区域有足够多的亮色像素（`AutoAlreadyOn` / `StoryAutoAlreadyOn`）。
- 点击节点 `AutoControlReady` 永远排在「已亮起」之后，要求灰色版模板 `auto_off_text.png` 在位且有文字像素（排除纯黑/模糊页面）才点一次。两个模板（阈值 0.8）互相只有约 0.41 的相似度，所以能分开开/关。
- 点击后等 1.5 秒看是否亮起；没亮只补点一次，再等 1.5 秒；仍没亮就放弃（`AutoGiveUp`），不再点击，交给战斗监控的超时处理。每次进入 AUTO 流程最多点两次，不循环。
- 复活会关闭 AUTO：`StoryPostReviveWait` 等 3.5 秒动画结束后再按同样规则判断（记忆回廊用 `TR_PostReviveWait`，补点后仍未亮起会弹窗停止）。
- 测试：`python tools/test_auto.py`（46 项）。

校准：用设备上的真实按钮裁剪图 `auto_on.png`（亮）和 `auto_off.png`（灰）贴到真实战斗截图的按钮位置测试：亮起时亮色像素 155、灰色时 0；有文字像素 321 / 158，所以阈值 190（亮）和 95（有文字）都能分开两种状态。没有验证的是整张"AUTO 关闭"的实机战斗截图和动画过程中的中间状态。
